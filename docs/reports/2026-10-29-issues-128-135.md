# Telepty #128–#135 repair and policy decisions

Base: PR #125, `2ead16824bf95ad33f8b183a042bf1fa44bf4409`. Public main fetched:
`67463584ee03ffd0337e94818d712804509294a3`. Work is an isolated local clone;
the existing Linux candidate checkout has an unrelated modified package-lock.json.
No installed daemon, credential, network configuration, remote branch or release is changed.

## Code repairs

- **#128:** postinstall launches this package's absolute `cli.js` using Node instead of
  the first PATH `telepty` shim. Detached spawn now has an error listener, returns a
  promise, and is awaited before the spawn-success log. Asynchronous ENOENT is caught
  and warned rather than rolling back npm through an unhandled error. This fixes
  the observed shim failure; it cannot guarantee recovery from every later daemon
  startup failure or keep the already-stopped old daemon alive. A successful spawn
  is not a readiness/version probe. Native Windows upgrade still needs validation.
- **#129:** all kill failure paths set `process.exitCode = 1` and return, allowing
  pending transport teardown to finish. Missing, HTTP-refused and transport-error
  branches have executable regression coverage. Missing-session exit remains 1.
- **#135:** HTTP registration already precedes startup. The bridge now additionally
  waits for a nonempty WS `owner_token` before spawning its command, recovering
  pending bridge messages, attaching terminal input or printing success. Initial
  claim wait is bounded to 10 seconds; timeout leaves the record untouched and
  starts no command. Frames received with the owner token are replayed after local
  child initialization. Reconnect retains the existing credential checks. Refusal
  still closes only the challenger, with no DELETE or mailbox purge.

## Unresolved observations and decisions

- **#130:** the isolated Linux duplicate-owner tests preserve the incumbent in the
  list as CONNECTED and it continues accepting injects. This does not reproduce
  the Windows refusal-then-not-found sequence. Do not infer a missing owner from a
  refusal, or issue a new bearer to a still-recorded session. Next evidence needed:
  exact host/port, session epoch, owner PID and lifecycle events around the refusal
  and subsequent list/kill. No automatic takeover or new assertion of owner liveness
  is added. Initial HTTP re-registration can still update descriptive incumbent metadata before
  WS refusal. The follow-up below now protects owner/PTY PID metadata with the existing
  session credential; other descriptive fields remain outside this scoped fix.
- **#131:** a new package's npm `preinstall` hook is not a reliable guarantee that
  the old globally installed tree is unlocked before npm replaces it. Adding one
  without proving npm's replacement ordering would overstate the fix. A supported
  Windows update workflow should stop and verify the old daemon *before invoking
  npm*, then install, verify the new package, and restore the previous supervisor
  ownership. On failure, report which step failed and offer explicit recovery;
  never treat EPERM cleanup warnings as proof of a correct installed tree. Direct
  `npm install -g` while the daemon holds files remains unaddressed. Native Windows
  npm-version matrix and supervisor tests are required before implementing it.
- **#132:** proposed opt-in principal mode: verified asymmetric identity maps to a
  stable principal ID, recorded on session creation with epoch. Keep the existing
  token mode explicitly single-principal for compatibility. Same OS account,
  loopback, session name, caller-provided `sub`, shared HS256 key possession and
  tailnet reachability must not manufacture distinct agent identities. Decide trust
  provisioning/revocation, verifier rules, operator recovery and migration first.
- **#133:** takeover remains denied by default. After #132 exists, an explicit
  takeover must require the same verified principal (or an explicit operator grant),
  atomically compare epoch/owner generation, gracefully hand off a live incumbent,
  rotate credentials, preserve sender/time on pending messages and audit the
  transition. TTY presence may confirm intent but cannot establish identity.
- **#134:** after principal mode exists, authorize POST kill and DELETE against the
  same owner/operator policy, deny with 403 and audit the decision. Internal reaping
  uses an explicit system actor. PR #125's optional owned DELETE does not authorize
  or restrict POST kill. Choosing compatibility default, operator grants and their
  provisioning is a product/security decision; no new policy is silently enabled.

## Follow-up investigation: #130 process identity protection

A separate Linux defect was reproduced without invoking kill: challenger B registers
an incumbent A's ID without its session token, receives no bearer and is refused with
WS 4003, but the register route previously replaced A's ownerPid with B's PID first.
After B exits the listed process identity points at the refused/dead challenger. This
can mislead diagnostics and later lifecycle operations; it is **not evidence** that
this caused the Windows refusal-then-not-found observation.

The follow-up gates `applyProcessMetadata(existing, req.body)` on the same existing
session-token/credentialless-legacy rule already used for delivery endpoints.
Credentialless, wrong-token and revoked-token callers cannot rewrite process targets;
the current owner can still refresh them on reconnect. No new principal, bearer,
takeover or kill-authorization policy is introduced.

Evidence: three direct route tests failed before the guard, as did the real isolated
bridge test (incumbent owner PID changed to challenger PID). After the fix, all five
route cases and the real bridge/credential issuance suites passed (21 tests). No real
PIDs are signalled by the direct tests; their numeric PIDs are inert metadata. The
integration fixture uses only its own ephemeral daemon and bridge processes. The
independent read-only reviewer found no important defects in this follow-up diff.

The original #130 not-found sequence remains unconfirmed. Needed Windows evidence:
exact daemon endpoint used by each command; same session epoch before/after refusal;
owner/PTY PID and their observed liveness; timestamped session reaping/destroy/restart
and WS-close events. Gather these read-only, without replacement, deletion or token
rotation. Neither an absent list entry nor a refused WS claim authorizes takeover.

## Follow-up investigation: #131 npm phase ordering

Inspected the already installed Linux npm **10.8.2**, not the Windows reporter's npm.
Its bundled Arborist `lib/arborist/reify.js` `reifyPackages` dispatcher orders:

1. `retireShallowNodes` moves existing package trees aside.
2. Sparse-tree creation and `unpackNewModules` prepare the new package.
3. `build` calls `rebuild`; `lib/arborist/rebuild.js` runs preinstall, bin links,
   install, then postinstall.
4. `removeTrash` removes retired trees after those lifecycle scripts.

An inert execution probe called the actual installed dispatcher with **every phase,
audit, filesystem operation, lifecycle invocation and rollback action replaced** by
journal callbacks. The normal trace matched the sequence above. Simulating EPERM in
retirement yielded only `retireShallowNodes → rollbackRetireShallowNodes`; no build or
hook ran. Probe source/output remain at `/tmp/telepty-npm-reify-order.js` and
`/tmp/telepty-npm-reify-order.json`. No package install, extraction, lifecycle script,
audit upload or daemon action was performed by the probe.

Consequences: preinstall might release handles before final trash removal in some
cases, but cannot protect the earlier retirement/replacement operations. Postinstall
already precedes final trash cleanup in this inspected npm version, so adding an
uninstall/preinstall hook alone is not an evidence-backed complete fix. The report's
Windows warning/log order does not establish which internal replacement phase or
which process held a handle; native Windows measurement remains necessary.

A safe complete updater needs a coordinator **outside the package being replaced**:
identify the installed tree and confirmed processes holding its native modules;
quiesce the applicable supervisor before replacement; handle live allow bridges that
may also map node-pty; verify the locks are gone; perform replacement; then restore
only the previously selected service owner after verifying the installed version.
A replacement failure needs durable recovery information outside the replaced tree.
Defaulting to taskkill of all node processes, disabling services, or silently killing
wrapped agents is not an acceptable inference from this issue. The current parent
scope prohibits live install/service changes, and no Windows execution environment
is available here. No such action was attempted, denied or left pending.

**#131 remains unresolved:** no package lifecycle workaround is presented as a fix.
Before implementing automatic quiescence, validate Windows/npm versions, identify
actual handle owners, and decide the explicit behavior for active wrapped sessions
and supervisor-managed installations. This follow-up adds only the safe #130 guard.
