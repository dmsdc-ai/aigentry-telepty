## 1. Mechanism map (goal 1)

### 1.1 The production launch path makes the singleton lock dead code

The installed plist (`~/Library/LaunchAgents/com.aigentry.telepty.plist`, generated by
`install.js:89-128` / `install.sh:88-110`) runs:

```
ProgramArguments = [ <…>/bin/telepty, daemon ]     # telepty → symlink → cli.js
```

`cli.js:1296-1303` handles bare `telepty daemon` by setting
`AIGENTRY_TELEPTY_DAEMON_MAIN=1` and calling `require('./daemon.js')`. Inside daemon.js
`require.main` is therefore **cli.js, never daemon.js**. Consequences:

| daemon.js | guard | runs in production? |
|---|---|---|
| `:382` `claimDaemonState(...)` — the singleton lock | `require.main === module` | ❌ **never** |
| `:4306` `app.listen(...)` | `require.main === module \|\| AIGENTRY_TELEPTY_DAEMON_MAIN === '1'` | ✅ yes |
| `:4435` mailbox stale-lock sweep + `mailboxDelivery.start()` | `require.main === module` | ❌ never |
| `:4476` idle-TTL reaper interval | `require.main === module` | ❌ never |
| `:4482` health/surface-GC poll interval | `require.main === module` | ❌ never |
| `:4706` `SIGINT`/`SIGTERM`/`exit` handlers (`clearDaemonState`) | `require.main === module` | ❌ never |

Only the listen block was ever given the `AIGENTRY_TELEPTY_DAEMON_MAIN` escape hatch — the
comment at `daemon.js:4299-4302` records that this exact class of bug (`0.5.0`
daemon-never-listened) was fixed *there and only there*.

**Evidence (live, non-invasive):** a daemon is running on 3848, yet
`~/.telepty/daemon-state.json` does not exist. The repro test asserts the same thing.
Corroborating: 1.3 MB of launchd daemon log contains **zero** `[MAILBOX]` / `[REAPER]` /
`[CLEANUP]` lines.

So the only arbitration between two daemons is first-come-first-served on the TCP port.

### 1.2 The CLI's spawn decision

`cli.js:754 ensureDaemonRunning` →
- probes `/api/meta` 3× with 200 ms backoff (`cli.js:768-782`) → **~600 ms total budget**;
- on total failure probes `/api/sessions` (5 s timeout, `cli.js:788-797`);
- `decideDaemonAction` (`cli.js:751`) returns `{action:'start', reason:'daemon-unreachable'}`;
- `restartDaemonGraceful` (`cli.js:458`) → `cleanupDaemonProcesses()` → `findPortOwnerPid` fail-fast →
  `startDetachedDaemon()` (`cli.js:426-434`) spawns `node <cli.js> daemon` **detached + unref'd**.

Nothing in that path asks whether a supervisor owns the daemon. The retry budget (~600 ms)
is far shorter than a real launchd relaunch (SIGKILL → exec → node boot → express init ≈ 1 s+
for this daemon.js), so an ambient CLI in the gap *reliably* decides "no daemon".

### 1.3 What the launchd-relaunched instance does on bind failure

`daemon.js:4640-4655`:

```js
server.on('error', async (error) => {
  clearDaemonState(process.pid);
  if (error.code === 'EADDRINUSE') {
    const probe = await fetch(`http://127.0.0.1:${PORT}/api/health`);
    if (data.status === 'ok') { console.log('… already running … Exiting.'); process.exit(0); }
    process.exit(1);
  }
```

It exits **0** — indistinguishable from a clean shutdown. Note the observed stdout ordering
(reproduced standalone): the loser prints the `🚀 … listening on …` banner *before* the
`already running` line, because the banner is emitted from the listen callback path while
the `error` handler fires asynchronously. Cosmetic, but it makes the launchd log lie about
who is serving.

launchd's `KeepAlive=true` then relaunches on its throttle, the relaunch loses the port
again, exits 0 again — a silent spin that never recovers. **There is no self-heal path.**

### 1.4 #733 version-mismatch interplay

`decideDaemonAction` (`cli.js:729-752`) delegates version policy to `decideVersionAction`
(`src/version-handshake.js`, newer-wins). Once an orphan exists, any CLI at a *newer*
version returns `{action:'restart'}` → `restartDaemonGraceful` → `cleanupDaemonProcesses`
(`daemon-control.js:370-418`), which sweeps the whole process table via
`isLikelyTeleptyDaemon` — the same blind `telepty-daemon` title match that bit me above —
kills the incumbent and spawns a replacement that is *again* outside launchd. That is the
#733 self-update war: every version-mismatched CLI re-creates the orphan, and launchd's own
instance can never win because it is always the one that arrives second.

## 3. Fix candidates, ranked against the repro (goal 4 — analysis only)

### Rank 1 — (b0, prerequisite) repair the `require.main` guards in daemon.js
Extend the `AIGENTRY_TELEPTY_DAEMON_MAIN` escape hatch (or compute one `IS_DAEMON_MAIN`
const) to `:382`, `:4435`, `:4476`, `:4482`, `:4706`.
- **Evidence:** §1.1; live `daemon-state.json` absent; repro asserts it.
- **Why first:** every lock-based fix presupposes a lock, and today there is none. It also
  restores mailbox delivery, the idle reaper, the health/GC poller, and the SIGTERM
  handlers, all currently dead in production. Cheap and purely additive.
- **Cross-platform:** neutral — pure JS, no OS calls (§2 satisfied trivially).
- **Caveat:** turning these on in production is a behaviour change well beyond #738's
  blast radius (dormant timers waking up on a live fleet). Wants its own ticket and its own
  test pass, even though #738's fix depends on it. **Recommend splitting.**
- **Alone it does NOT fix #738:** `claimDaemonState` is first-come-first-served too, so the
  CLI's daemon would simply claim the state file first and the supervisor would exit at
  `:387` instead of `:4649`. Same orphan, different exit line.

### Rank 2 — (a) supervisor-aware CLI: detect, then defer
In `ensureDaemonRunning`, before `action:'start'`, probe for a supervisor that owns the
daemon; if present, **wait** for it (bounded, e.g. 10 s) instead of spawning, and only fall
back to spawning if the supervisor never produces a daemon.
- **Evidence:** directly closes the repro's causal step — the RED test already pins exactly
  this contract, and its discovery surface (a plist in `HOME`) is the real one.
- **Cross-platform (§2 — the load-bearing design point):** split *detection* (per-OS) from
  *policy* (uniform). Detection: macOS `~/Library/LaunchAgents/com.aigentry.telepty.plist`;
  Linux `systemctl --user is-enabled telepty` or the unit file `install.js:136-160` writes;
  Windows `schtasks /query /tn <task>` (`install.js:180`). Policy is identical everywhere:
  *supervisor present ⇒ defer-and-wait; absent ⇒ today's spawn.* On a platform with no
  supervisor installed, behaviour is byte-identical to today.
- **Recommended over the brief's "delegate via `launchctl kickstart`" variant:**
  delegation is mac-only *and* re-runs the very command that opens the gap. Defer-and-wait
  is portable and passive.
- **Risks:** a disabled/broken supervisor costs a bounded wait before the fallback spawn
  (mitigate: cache the "supervisor didn't deliver" verdict, mirroring the
  `restart-failure.json` marker at `daemon-control.js:327-355`). Detection must be cheap —
  it runs on every CLI invocation; an `fs.existsSync` (macOS) is fine, a `schtasks`/
  `systemctl` shell-out per command is not, so cache it per process.

### Rank 3 — (b) startup lockfile / handshake with supervisor priority
Give the supervisor-launched instance the right to *evict* an incumbent rather than exit 0.
- **Evidence:** would also cover the non-supervisor case (two ambient CLIs racing), which
  (a) leaves untouched.
- **Blocker to solve first:** the instance must be able to prove it is supervisor-launched.
  launchd exports `XPC_SERVICE_NAME=com.aigentry.telepty` into the job environment and
  systemd exports `INVOCATION_ID`/`JOURNAL_STREAM` — both usable, zero-config. **Windows
  `schtasks` exports no comparable marker**, so §2 parity would need the supervisor
  definition itself to inject an explicit env var (e.g. `TELEPTY_SUPERVISED=1`) at install
  time — which then only helps hosts that *reinstall* the service. That upgrade-migration
  tail is why this ranks below (a).
- Depends on Rank 1 to have a lock at all.

### Rank 4 — (c) spawned daemon inherits the launchd log path
- **Mitigation only.** It makes the orphan visible in the logs; the orphan still exists,
  still sits outside launchd, still fuels #733. Worth doing as a diagnostic, never as *the*
  fix. Cheap and portable (pass the resolved log path through `startDetachedDaemon`).

**Recommendation:** ship **Rank 2 (a)** as the #738 fix — it is what the RED test pins — and
file **Rank 1 (b0)** as its own high-priority ticket (it is a larger, independent
production-behaviour change). Revisit Rank 3 once (b0) lands.
