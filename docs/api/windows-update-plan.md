# Windows self-update guard and external recovery plan

`telepty update` on Windows refuses before npm, custom update overrides or daemon repair can run. The interactive update action shares the same producer guard. The process cannot prove that the old installation has no mapped-file/native-module holders, that a daemon PID belongs to the matching installation, that the scheduled task is owned by that installation, or that a failed upgrade can be completely rolled back. A task name, a PID and the legacy state file's port/version are insufficient stop authority.

`telepty update --plan --json` produces a bounded read-only assessment. The text form is `telepty update --plan`. Planning reads only bounded package/state files, projects non-secret metadata, labels process/service ownership unknown, and performs no npm, process scan/signal, service-manager, network, credential, backup or installation action. An absent, corrupt, linked or oversized state file never becomes permission to stop a process. No override silently claims the installation was quiesced.

The returned manual plan names the prerequisites for an external coordinator: inspect exact installation/Node/service ownership from outside the tree; record prior running state; finish or preserve work and explicitly release matching bridges/native holders; let the old CLI exit; prepare a verified external backup and durable recovery journal; then perform the chosen external upgrade. Restart only the previously running matching daemon/service after verified success, or after a verified complete rollback. Leave originally stopped services stopped. A partial or unverifiable rollback must remain quiesced with manual recovery required.

This guard does not intercept `npm install -g` invoked directly. The repository's preuninstall hook explicitly documents that npm 7+ does not run uninstall lifecycle scripts; a new package's preinstall/postinstall cannot guarantee stopping the old installation before npm removes it. The old daemon version in issue #131 also has no verified installation/birth-bound quiescence protocol. Adding a new hook or an unverified PID kill would not fix that ordering safely.

No native Windows mapped-file verifier, cross-process transaction/rollback protocol or automatic external worker is claimed. Native direct-npm upgrades remain unresolved. Non-Windows update execution keeps its existing behavior; the read-only plan does not certify that path as transactional or safe against every concurrent holder.
