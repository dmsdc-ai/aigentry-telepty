# Durable transport ACK settlement for consented handoff

A successful pending-handoff receipt measures one bridge `child.write` invocation. It does not establish physical PTY byte delivery, consumption, an agent answer or task completion. `pending_dispatch_started` alone remains uncertainty; even `pending_write_invoked` is insufficient without mailbox ACK evidence.

Previously, a strict inbox row plus `acked` journal row could establish known transport settlement, but normal compaction removed both rows. Their absence deliberately could not establish settlement, so the handoff namespace remained reserved. That old negative behavior is retained for generic/legacy ACKs and old compacted queues.

The new path captures an opaque in-process result only after the daemon accepts the exact owner/request/epoch/intent/message/hash-bound `child_write_invoked` receipt. The private result capability is consumed after `pending_write_invoked` is durably saved. A serialized object or caller-supplied boolean cannot create it. DeliveryEngine passes that same result object to mailbox ACK; ordinary HTTP/mailbox ACK APIs do not receive this capability.

Under the existing mailbox lock, trusted ACK verifies the exact current message and non-retryable in-flight history, appends and fsyncs the ACK journal, then publishes a private `handoff-settlements.jsonl` snapshot by exclusive temporary file, file fsync, atomic rename and directory fsync. Only after that succeeds may normal compaction remove ACK/inbox rows. A one-use capability binds exact SID, successor epoch, original epoch/owner generation, intent, batch digest and message digest. Records explicitly state `bridge_child_write_invoked`, `mailbox_state:acked`, and consumption/reply unknown. They contain no raw message content, bearer, private key or original signature.

The ledger is never automatically compacted or expired. It is bounded to 512 records and 512 KiB per mailbox; exhaustion fails closed and retains existing evidence. Duplicate proof use cannot add records. Read-back validates strict bounded JSON, unique keys/records, file stability and scope. Existing visible proof files are fsynced again before namespace release, so a prior uncertain durability call is not treated as a successful flush.

Namespace release requires every retained message's durable `pending_write_invoked` and either current strict ACK/inbox evidence or an exact new settlement record after compaction. The session epoch must still match the handoff's successor epoch. Missing/old/mismatched/corrupt proof never substitutes for empty custody. Any explicit unknown journal or DLQ history overrides both old ACKs and new settlement records. Unknown payload/history is preserved through compaction.

Pre/post-rename proof failures do not authorize another physical send. ACK failure records unknown history while retaining the original inbox payload, and DeliveryEngine reports storage uncertainty instead of successful settlement. A visible proof from a post-rename failure is preserved, but cannot override that unknown history. No repair or migration of an operational mailbox is performed.

This is a trusted local evidence file using the same private mailbox filesystem boundary, not cryptographic at-rest authentication against a privileged filesystem editor. The change rejects forged serialized result capabilities and mismatched/ambiguous persisted evidence; it does not claim that correctly forged files written by an actor controlling the mailbox directory are authentic. The new proof adapter is Linux-only and fails closed on unsupported platforms. Linux private-filesystem tests cover the durability sequence; no native Windows/macOS acceptance is asserted.
